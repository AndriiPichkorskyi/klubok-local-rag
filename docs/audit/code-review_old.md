# Аудит коду (Code Review)

## 1. Мовчазна втрата даних при збоях запису локальної довідки
**Файл:** `sidecar/src/modules/indexer/pipeline.js`
**Локація:** Функція `runFetchLocalDocsLocked`, рядок ~694
**Дефект:** Помилки від `db.saveWebDocument(linkId, content)` та наступного `UPDATE apps...` перехоплюються порожнім блоком `catch (err) { }` і повністю ігноруються.
**Сценарій:** Якщо база даних переведена в режим read-only (наприклад, через проблеми з правами доступу), пошкоджена, або на диску закінчилося місце, запис документації впаде з помилкою. Проте через порожній `catch`, система мовчки продовжить ітерацію. Лічильник прогресу просуватиметься, а після завершення сканування користувач вважатиме, що довідка проіндексована, хоча локальні HTML-файли так і не потрапили в `web_documents`.
**Серйозність:** Середня (часткова втрата даних виглядає як успіх).

## 2. Некоректний підрахунок pass rate у RAG-бенчмарку
**Файл:** `sidecar/src/tests/test-rag.js`
**Локація:** Блок обробки `isAlternativeSuccess`, рядки ~310-340.
**Дефект:** Якщо LLM обирає абсолютно неправильну програму (галюцинує), але правильна програма просто *присутня* у векторному контексті (`result.contextApps`), тест вважає це частковим успіхом (`isAlternativeSuccess = true`) і збільшує `passed++`.
**Сценарій:** Запускається RAG-бенчмарк. Векторний пошук спрацьовує ідеально, кладучи цільову програму на 3-тю позицію контексту. Проте LLM не справляється і відповідає, що для запису екрана найкраще підійде "Калькулятор". Оскільки цільова програма була в `contextApps`, умова `isAlternativeSuccess` виконується і тест зараховує цей кейс як "Успішно" (`passed++`). У результаті `passRate` відображає якість векторного пошуку, маскуючи повну деградацію LLM-генерації. 
**Серйозність:** Висока (результатам бенчмарку щодо якості LLM не можна довіряти).

## 3. Маскування валідного виводу LLM при помилці форматування
**Файл:** `sidecar/src/modules/rag/engine.js`
**Локація:** Блок парсингу відповідей (`config.rag.enableJsonFormat = false`), рядок ~230.
**Дефект:** Якщо модель генерує розгорнуту та правильну відповідь, але забуває додати тег `[SOURCE_ID: X]`, змінна `recommendedApp` лишається `null`. Через це код повністю відкидає згенерований текст `responseText` і замінює його на жорстко закодовану заглушку: *"На жаль, я не знайшов на вашому Mac програми..."*. 
**Сценарій:** Користувач задає питання. Локальна Qwen3:1.7b генерує ідеальний опис того, як використати програму, але не ставить технічний тег `[SOURCE_ID: 1]`. Замість того, щоб отримати текст від моделі, користувач отримує системне повідомлення про те, що програму не знайдено (хоча LLM її насправді знайшла і описала). 
**Серйозність:** Середня (серйозна деградація UX при використанні менших локальних моделей).

## 4. Потенційний нескінченний цикл при розбитті на чанки (Chunking)
**Файл:** `sidecar/src/modules/indexer/chunker.js`
**Локація:** Цикл `while (i < text.length)` у функції `chunkText`, оновлення `i = end - chunkOverlap;`
**Дефект:** Оновлення кроку циклу базується на `chunkOverlap`. Якщо з будь-якої причини `chunkOverlap` буде налаштовано на значення, що дорівнює або перевищує `chunkSize` (або `end - i`), змінна `i` перестане зростати.
**Сценарій:** Користувач (або інший агент) експериментує з параметрами векторного пошуку і прописує в `pipeline.config.json` значення `chunkSize = 500` і `chunkOverlap = 500` (або просто дуже великий overlap). Процес індексації доходить до великого тексту, `i` оновлюється як `i = end - 500`, що повертає його на ту саму позицію. Бекенд-процес (sidecar) зависає назавжди зі споживанням CPU 100%, блокуючи будь-які інші операції.
**Серйозність:** Низька (вимагає ручного втручання в конфіг, але наслідки фатальні).
