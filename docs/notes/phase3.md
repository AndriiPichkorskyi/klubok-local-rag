# Фаза 3 — модуль 2.4.2 (панель розробника)

Нотатки агента, що портував термінальне меню `sidecar/src/cli/index.js` у React.
Виправлень поза `src/dev/` не робив — усе нижче лише зафіксовано.

## Виправлено у фундаменті (координатор), панель уже працює на новому контракті

- **Мітка `ref` у прогресі.** `rpc(method, params, clientRef)` + `newRef()` в `src/ipc.js`,
  Rust додає `ref` у кожну подію `sidecar://progress`. Панель більше не вгадує власника
  прогресу: кожна операція фільтрує події за своїм `ref` (`useDevRuntime.js`). Прогрес
  без `ref` або з чужим (наприклад, `query` зі Spotlight) іде лише у спільний журнал.
- **`reports.read({name})`.** Клік по звіту читає файл і будує таблицю; тимчасове поле
  для ручного вставляння JSON прибрано.
- **`rpc.requestTimeoutSec` = 7200.** Повна векторизація більше не впирається в 600 секунд.

## Чинні баги і розбіжності

- **`job.cancel` приймає серверний `id`, якого фронтенд не знає наперед.** `ref` однозначний,
  але зіставлення `ref → id` доступне лише з першої події прогресу, тож кнопка скасування
  з'являється не одразу після старту (для операцій без прогресу — не з'явиться зовсім).
  Достатньо було б повертати `id` з `rpc_call` або приймати `ref` у самому `job.cancel`.
  Сам метод усе одно повертає `cancelled:false` — це вже описано в `improvements.md`.

- **Тести не віддають прогрес.** У `sidecar/src/rpc/methods.js` методи `tests.run` і
  `tests.runExternal` викликають `runRagTests()` / `runExternalTests()` без `ctx.onProgress`.
  Весь вивід іде в термінал sidecar, а в панелі під час тестування видно лише лічильник часу.

- **`tests.run` повертає булеве значення.** `runRagTests()` завершується `return !anyFailed`,
  тож результат методу — `true`/`false`, а не об'єкт. Запобіжник `?? { ok: true }` на `false`
  не спрацьовує. Панель трактує `false` як «є провалені кейси».

- **Старі звіти ламають підсумок токенів.** У звітах до 2026-08-25 у `summary` немає
  `totalInputTokens` / `totalOutputTokens`, і `renderReportTable()` у CLI друкує для них
  `undefined / undefined`, а підсумковий рядок — `NaN`. У `ReportTable.jsx` такі поля
  показані прочерком.

- **`pipeline.vectorize` ігнорує `params`.** Метод завжди бере `config.embedModelName`
  (EMBED_MODEL читається один раз при старті процесу), тож векторизувати конкретну модель
  окремим кроком неможливо: єдиний шлях для «чужої» моделі — `pipeline.fullSync({models})`,
  який усередині ще раз проганяє кроки 1–4. Наслідок для комбінованого прогону: крок
  «Вектори · <інша модель>» коштує повного пайплайна, і панель про це попереджає текстом.
  Достатньо було б приймати `{model}` у `pipeline.vectorize`.

- **Назви цілей очистки різні в CLI і в RPC.** У меню CLI значення `clear_web` / `clear_local`,
  у контракті `db.clear` — `web` / `local`. Панель користується назвами з контракту.

## Рішення, які варто пам'ятати

- Методи контракту, не задіяні панеллю: `query` (це модуль 2.4.1) і `bootstrap.pullModel`
  (CLI моделі не тягне, лише радить виконати `ollama pull` — порт «один в один»).
- Підтвердження деструктивних дій — власний компонент `ConfirmDialog.jsx`.
  `confirm()`/`alert()`/`prompt()` не використовуються ніде: вони блокують застосунок.
- Журнал прогресу тримає останні 2000 рядків, але обрізання зрізає ЛИШЕ рядки рівня
  `progress` — старти, завершення, скасування і помилки лишаються видимими, навіть якщо
  між ними пройшли тисячі рядків векторизації. Скільки зрізано, панель показує позначкою:
  мовчазна втрата рядків була б гіршою за їхню відсутність.
