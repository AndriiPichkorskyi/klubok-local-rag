# Висновки з великих прогонів 02–03.09.2026

Цей документ фіксує результати прогонів парного українсько-англійського набору
EXTERNAL-тестів: початкового невалідного порівняння моделей, факторного
порівняння режимів і повторної матриці моделей після виправлення. Він доповнює,
але не замінює
[`testing-conclusions.md`](testing-conclusions.md), де описані експерименти від
29.08.2026 на іншому наборі та з іншою конфігурацією.

## Короткий висновок

1. Перший прогін, задуманий як порівняння chat- та embedding-моделей, **не можна
   використовувати для такого порівняння**. Усі 12 звітів фактично створені
   парою `qwen3:1.7b` + `qwen3-embedding:4b`, тому вони не є матрицею моделей.
2. Другий прогін є повною факторною матрицею з 36 режимів і 2448 завершених
   викликів. Він показав, що спосіб пошуку та переупорядкування контексту мають
   значно більший зв’язок з успішністю, ніж XML або місце системного промпту.
3. Векторний пошук по україномовній базі добре працює з англійськими запитами:
   `63.89%` успіху проти `59.34%` для українських. Лексичний FTS на англійських
   запитах падає до `12.63%`. Це підтримує гіпотезу про кросмовну придатність
   багатомовних ембедингів у локальному RAG.
4. Повторний експеримент після виправлення RPC є валідною матрицею 4 × 3 із
   2448 результатів. Найкраща пара — `qwen3:1.7b + qwen3-embedding:4b`:
   `63.98%` успіху на прикладних задачах. Моделі chat до приблизно 1B не
   перевищили `12.90%`.
5. `qwen3-embedding:0.6b` досягла `77.42%` retrieval recall проти `82.26%` у
   4B-моделі та `74.19%` для англійських запитів по українському корпусу. Це
   найперспективніше місце для економії локальних ресурсів.

## Тестовий набір

Кожен режим містив 68 кейсів:

| Мова | Кейсів на режим | Призначення |
|---|---:|---|
| українська | 33 | запити до україномовної бази тією самою мовою |
| англійська | 33 | парні за змістом кросмовні запити |
| нейтральна | 2 | запити, де мова не впливає на формулювання |

Українські й англійські кейси мають спільні `comparisonId`, тому їх можна
порівнювати попарно. Успішність означає, що LLM рекомендувала одну з програм,
зазначених у `expectedApp`. Для EXTERNAL-набору наявність правильної програми
лише серед знайдених документів не зараховується як успішна відповідь.

## Експеримент 1: задумана матриця моделей

### Початковий задум

Повний прогін у UI мав створити окремий звіт для кожної вибраної пари chat- та
embedding-моделей. Усередині кожної пари фіксувалися такі параметри:

| Параметр | Значення |
|---|---|
| пошук | `hybrid` |
| XML | увімкнено |
| reorder | увімкнено |
| системний промпт | `inline` |
| seed | `1`, `2`, `3` |
| temperature | `0.1` |
| паралельність | 2 потоки |

Один звіт: 3 режими × 68 кейсів = 204 виклики LLM. Усього отримано 12 звітів,
тобто 2448 результатів.

Група звітів:

- `sidecar/test-reports/prev2/report-external-2026-09-02T22-00-18-836Z.json`
  … `report-external-2026-09-03T01-14-30-420Z.json`;
- `sidecar/test-reports/report-external-2026-09-03T01-33-44-614Z.json`.

### Виявлена помилка

У всіх 12 файлах поле `models` однакове:

```text
chat:  qwen3:1.7b
embed: qwen3-embedding:4b
```

Усі звіти також мають однаковий профіль успішності за seed: `65%`, `66%`,
`65%`. Причина встановлена в коді: `fullRunPlan.js` передавав
`overrideChatModel` і `overrideEmbedModel`, але RPC-методи `tests.run` та
`tests.runExternal` не передавали ці поля у функцію тестування. Після цих
прогонів помилку виправлено.

### Що з цих даних можна використовувати

Ці 12 звітів **не вимірюють вплив розміру або типу моделей**. Порівнювати їх як
12 різних пар науково некоректно.

Їх можна використати лише як допоміжне спостереження повторюваності однієї
конфігурації. В одному триразовому прогоні:

| Seed | Успішність |
|---:|---:|
| 1 | 64.71% (44/68) |
| 2 | 66.18% (45/68) |
| 3 | 64.71% (44/68) |
| середнє | 65.33% |
| стандартне відхилення | 0.47 в.п. |

Pass rate стабільний, але сирий вивід не є детермінованим: при попарному
порівнянні seed побайтово однаковими були лише 89 із 204 відповідей (`44%`).
Отже, модель часто змінює текст, зберігаючи те саме класифікаційне рішення.

### Мовний результат цього прогону

| Мова | Успішність за трьома seed |
|---|---:|
| українська | 62.63% |
| англійська | 65.66% |
| різниця UK − EN | −3.03 в.п. |

Це узгоджується з кросмовною гіпотезою, але не є незалежним порівнянням
embedding-моделей.

## Експеримент 2: повна факторна матриця RAG

Основний звіт:
`sidecar/test-reports/report-external-2026-09-03T06-25-53-157Z.json`.

### Конфігурація

| Вісь | Значення |
|---|---|
| пошук | `hybrid`, `fts`, `vector` |
| XML | `true`, `false` |
| reorder | `true`, `false` |
| системний промпт | `inline`, `system`, `none` |
| seed | `42` |
| temperature | `0.1` |
| chat model | `qwen3:1.7b` |
| embedding model | `qwen3-embedding:4b` |
| паралельність | 2 потоки |

Повний добуток осей: 3 × 2 × 2 × 3 = 36 режимів. Отримано 2448 із 2448
очікуваних результатів, тобто повнота звіту становить `100%`.

### Загальний результат за способом пошуку

Значення нижче усереднені за XML, reorder і розміщенням системного промпту.

| Пошук | Успішність | Різниця від FTS |
|---|---:|---:|
| `vector` | **62.75%** | +32.72 в.п. |
| `hybrid` | 57.23% | +27.21 в.п. |
| `fts` | 30.02% | — |

Спосіб пошуку — найсильніший із досліджених факторів. `vector` показав
найкращий середній результат, а FTS програв йому більш ніж удвічі за часткою
успішних відповідей.

### Кросмовний пошук

| Пошук | Українська | Англійська | UK − EN |
|---|---:|---:|---:|
| `vector` | 59.34% | **63.89%** | −4.55 в.п. |
| `hybrid` | 55.56% | **56.31%** | −0.76 в.п. |
| `fts` | **43.18%** | 12.63% | +30.56 в.п. |

Документація в базі українською, але vector і hybrid не деградують на
англійських формулюваннях. Навпаки, англійські парні запити дали трохи вищий
результат. Водночас FTS, який залежить від збігу слів, утрачає 30.56 в.п.
між українською та англійською.

Захищене формулювання для дипломної роботи:

> На парному наборі з 33 українських і 33 англійських задач векторний пошук по
> україномовному корпусу не показав погіршення для англійських запитів
> (63.89% проти 59.34%), тоді як успішність лексичного FTS знизилася з 43.18%
> до 12.63%. Результат підтримує доцільність багатомовних ембедингів для
> локального кросмовного пошуку без попереднього перекладу документації.

Це твердження стосується конкретного набору, моделей і локальної бази. Воно не
доводить однакову якість для всіх мов або предметних областей.

### Вплив решти факторів

| Фактор | Значення | Успішність |
|---|---|---:|
| reorder | `true` | **54.58%** |
| reorder | `false` | 45.42% |
| XML | `false` | **50.49%** |
| XML | `true` | 49.51% |
| системний промпт | `inline` | **50.25%** |
| системний промпт | `none` | 50.00% |
| системний промпт | `system` | 49.75% |

Reorder пов’язаний із приростом `9.15` в.п. XML змінив середній результат лише
на `0.98` в.п., а максимальна різниця між способами розміщення системного
промпту становить `0.49` в.п. Через єдиний seed ці числа треба трактувати як
описовий результат, а не як оцінку статистичної значущості.

### Найкращі режими

Два режими дали 47 успішних відповідей із 68 (`69%`):

| Режим | Середній час запиту |
|---|---:|
| `hybrid + reorder + XML off + inline` | 11.72 с |
| `hybrid + reorder + XML off + none` | 12.19 с |

За цим одиничним прогоном `inline` є кращою базовою конфігурацією: та сама
успішність і трохи менший середній час. Різницю часу не слід узагальнювати без
повторів, бо паралельний запуск і загальносистемне навантаження створюють шум.

Практичний компроміс дає `vector + reorder + XML off`: `66%` успішності за
середнього часу близько `6.3–6.6` с залежно від розміщення промпту. Тобто він
втрачає приблизно 3 в.п. від найкращого hybrid-режиму, але майже вдвічі
швидший. Це кандидат для Pareto-порівняння «якість — час — ресурси».

### Чутливість сирого виводу

| Вісь | Попарних результатів | Побайтово однакові | Вивід змінився |
|---|---:|---:|---:|
| пошук | 2448 | 13% | 87% |
| XML | 1224 | 16% | 84% |
| reorder | 1224 | 20% | 80% |
| системний промпт | 2448 | 41% | 59% |

Усі осі впливають на сформований текст. Невелика різниця pass rate для XML і
системного промпту не означає, що вони інертні: вони часто змінюють відповідь,
але рідко змінюють назву рекомендованої програми.

- якщо правильної програми немає серед переглянутих документів — проблема на

Останній пункт важливий: частина задач допускає кілька коректних програм.
Перед включенням pass rate в диплом треба вручну переглянути постійні провали
та зафіксувати правило, за яким альтернативи додаються до еталона.

## Обмеження двох прогонів

- Перший експеримент не перемикав моделі через помилку RPC.
- У другому експерименті кожна комбінація виконана лише з `seed=42`; для
  перевірки стійкості ефектів потрібні повтори.
- Старі звіти не містять SHA-256 тестового набору, digest і квантизацію моделей,
  версію ОС, CPU та Node. Ці поля додані лише для наступних прогонів.
- GPU вимірювався для всієї системи, а не окремо для Ollama.
- 68 кейсів походять з одного прикладного домену та однієї машини macOS.
- Pass rate залежить від повноти й коректності `expectedApp`; функціонально
  прийнятна альтернатива може виглядати як помилка тесту.
- Агреговані ефекти факторів не замінюють аналіз їхніх взаємодій. Наприклад,
  vector має найкраще середнє, але найкраща окрема комбінація використовує
  hybrid.

## Повторний експеримент 1 після виправлення перемикання моделей

Повторний прогін задуманої матриці завершено. Проаналізовано 12 звітів від
`2026-09-03T11-08-08-809Z` до `2026-09-03T13-15-38-150Z`: чотири
chat-моделі × три embedding-моделі. Кожна клітинка містить три повтори з
`seed=1,2,3` по 68 кейсів, тобто 204 результати. Загалом отримано 2448
результатів.

Фіксовані налаштування:

```text
test set:       EXTERNAL bilingual, 68 cases
search:         hybrid
xml:            false
reorder:        true
systemPrompt:   inline
seed:           1, 2, 3
temperature:    0.1
concurrency:    1
```

### Перевірка валідності

- усі 12 очікуваних пар моделей присутні;
- усі звіти повні: 204/204, без пропущених результатів;
- `datasetHash` однаковий у всіх звітах:
  `5b3dfea6bf78daeff70af0c11c1d05edecbd182aa75c24f702de0b9815ecee66`;
- середовище однакове: Apple M3, 8 логічних CPU, 16 ГБ unified memory,
  macOS `25.6.0`, Node `v24.7.0`;
- `models`, `modelDetails` і `modes.*.params` узгоджені та підтверджують
  фактично використані моделі;
- стандартне відхилення загального pass rate між трьома seed для кожної пари
  не перевищує 1.39 відсоткового пункту;
- покриття одночасно GPU- і RAM-метриками становить 76.47–100%; у 9 із 12
  звітів воно перевищує 93%.

Верхнє поле `axes.chatModel/embedModel` у 11 із 12 файлів помилково містить
дефолтну пару з конфіга. Воно не використовувалося в аналізі. Джерелом правди
були узгоджені поля `models`, `modelDetails` і `modes.*.params`.

`gemma3:270m` не назвала конкретної програми в жодній із 558 прикладних
спроб. `qwen3:0.6b` відхилила 530 із 558 нормальних задач як `NOT_FOUND` або
`INVALID_QUERY`. Її результат залишається низьким навіть із найкращим
retrieval: 4.30% із Qwen 4B. Отже, провал останнього звіту не можна пояснити
лише слабшим `nomic`: головна межа цієї конфігурації — рішення chat-моделі.

Серед протестованих моделей лише `qwen3:1.7b` показала рівень, який можна
розглядати як практично корисний. Однак експеримент порівнює не лише кількість
параметрів, а й різні сімейства та квантизації. Тому коректне формулювання для
диплома — «виявлено різкий приріст між протестованими моделями приблизно 1B і
2B», а не універсальна причинна межа у 2 мільярди параметрів.

### Внесок embedding-моделі та мови

Retrieval не залежить від chat-моделі, тому для кожної embedding-моделі маємо
186 унікальних запусків на трьох seed:

| Embedding | Параметри | Українська | Англійська | Разом | Прикладний pass rate по всіх chat-моделях |
|---|---:|---:|---:|---:|---:|
| `qwen3-embedding:4b` | 4.0B, Q4_K_M | 75/93 (80.65%) | 78/93 (83.87%) | **153/186 (82.26%)** | 146/744 (19.62%) |
| `qwen3-embedding:0.6b` | 595.78M, Q8_0 | 75/93 (80.65%) | 69/93 (74.19%) | **144/186 (77.42%)** | 128/744 (17.20%) |
| `nomic-embed-text:latest` | 137M, F16 | 51/93 (54.84%) | 24/93 (25.81%) | 75/186 (40.32%) | 62/744 (8.33%) |

Мала Qwen embedding-модель відстає від 4B лише на 4.84 відсоткового пункту
retrieval загалом і знаходить правильну програму для 74.19% англійських
запитів по українському корпусу. Це сильне емпіричне підтвердження того, що
для локального багатомовного пошуку модель приблизно 0.6B може бути достатньою.
Натомість Nomic втрачає 36.87 відсоткового пункту відносно Qwen 0.6B загалом,
а для англійської — 48.38 пункту. Саме Nomic створює помітний кросмовний
розрив у попередньо розглянутому останньому звіті.

Найкраща chat-модель також показує взаємодію з retrieval: для
`qwen3:1.7b` перехід Qwen 4B → Qwen 0.6B → Nomic знижує прикладну успішність
з 63.98% до 51.08% і 25.27%. Отже, сильніша LLM не компенсує відсутність
правильної документації в контексті.

### Ресурси та стійкість

Середній час chat-моделей змінюється від 0.58 с для непридатної
`gemma3:270m` до 7.68 с для найякіснішої `qwen3:1.7b`. Найкраща конфігурація
`qwen3:1.7b + qwen3-embedding:4b` має середній час 7.86 с, p95 12.31 с,
38.02 токена/с і середню RAM процесів Ollama 5198 МБ.

Малі стандартні відхилення pass rate між seed показують стійкість саме оцінки
якості, хоча текст відповідей не є детермінованим. RAM охоплює всі процеси
Ollama, а GPU є загальносистемним показником macOS; їх слід трактувати як
навантаження конфігурації на цій машині, а не як ізольоване споживання однієї
моделі.

### Висновок для дипломної роботи

> Повний факторний експеримент із 12 комбінаціями моделей і 2448 запусками
> розділив вплив пошуку та генеративного рішення. У досліджуваному пайплайні
> chat-моделі до приблизно 1B параметрів виявилися недостатніми: їхня
> успішність на прикладних задачах не перевищила 12.90% навіть за високого
> retrieval recall. Модель `qwen3:1.7b` досягла 63.98% з embedding Qwen 4B і
> 51.08% з Qwen 0.6B. Водночас `qwen3-embedding:0.6b` забезпечила 77.42%
> retrieval recall та 74.19% для англомовних запитів по україномовному
> корпусу, лише помірно поступившись 4B-моделі. Це обґрунтовує архітектурний
> компроміс: економити ресурси доцільніше на embedding-моделі, а не на
> chat-моделі, яка виконує фінальне ранжування та відхилення запитів.

Наступним доцільно запускати контрольний тест із більшою chat-моделлю, не
змінюючи набір кейсів, Qwen embedding 4B, retrieval-конфігурацію, seed,
temperature й один потік. Він покаже верхню межу якості та дозволить оцінити,
чи 63.98% обмежені розміром `qwen3:1.7b`, даними або тестовою розміткою.

## Твердження, які вже можна використовувати

З достатнім застереженням можна стверджувати:

- векторний пошук істотно перевершив FTS на парному двомовному наборі;
- Qwen embedding забезпечив пошук англійських запитів по українському корпусу
  без явного перекладу; для 0.6B-моделі retrieval recall становить 74.19%;
- reorder дав найбільший позитивний описовий ефект серед параметрів побудови
  промпту;
- XML і спосіб передачі системного промпту часто змінюють текст відповіді, але
  майже не змінюють агрегований pass rate;
- найкраща якість і найкращий час отримані різними конфігураціями, тому локальну
  систему треба оцінювати за Pareto-компромісом, а не лише за успішністю;
- Qwen embedding 0.6B відстає від Qwen 4B лише на 4.84 відсоткового пункту
  retrieval recall і є обґрунтованим ресурсним компромісом;
- `qwen3:0.6b` є практично непридатною chat-моделлю з усіма трьома перевіреними
  embedding-моделями, а не лише в парі з Nomic;
- `qwen3:1.7b + qwen3-embedding:4b` — найякісніша з перевірених конфігурацій:
  63.98% на прикладних задачах.

Поки що не можна стверджувати:

- універсальну мінімальну кількість параметрів chat-моделі: для цього треба
  наперед визначити поріг достатності й порівняти моделі одного сімейства;
- що Qwen embedding 4B статистично необхідна: мала модель уже близька до неї,
  а практичний вибір залежить від допустимого компромісу якості та ресурсів;
- що різниця близько одного відсоткового пункту статистично значуща;
- що виміряні GPU та RAM належать окремій моделі;
- що отримані відсотки узагальнюються на інші ОС, мови або корпуси.
